Software Design Document • DA-2 1. Design Principles: Abstraction & Modularity

1. Design Principles Applied

High-quality software architecture is grounded in four fundamental design principles: Abstraction, Modularity, High Cohesion, and Low Coupling. HabitForge implements these principles across both backend and frontend layers.

A. Abstraction (Hiding Complexity Behind Defined Contracts)

Abstraction guarantees that components interact through high-level functional contracts rather than brittle low-level implementations. In HabitForge:

  • Interface Contracts: Operations are exposed through Java interfaces like HabitService and StreakStrategy. Callers are unaware of whether data is stored in MongoDB or an in-memory cache.
  • Data Transfer Object (DTO) Boundary: Entities are never exposed directly to REST clients. HabitRequestDto and HabitResponseDto abstract API payloads, preventing clients from spoofing internal streak attributes.
// HabitService.java - Business Interface Contract (Abstraction)
package com.example.HabitForge.service;

public interface HabitService {
    HabitResponseDto createHabit(String userId, HabitRequestDto request);
    HabitResponseDto completeHabit(String habitId, String userId);
    List<HabitResponseDto> getUserHabits(String userId);
    void deleteHabit(String habitId);
}

// StreakStrategy.java - Strategy Pattern Interface
public interface StreakStrategy {
    int calculateNewStreak(Habit habit, LocalDate completionDate);
    boolean isStreakBroken(Habit habit, LocalDate currentDate);
}

B. Modularity (Autonomous, Reusable Functional Units)

Modularity decomposes the system into loosely coupled packages that can be modified, tested, and deployed independently:

Backend Spring Boot Modules:
  • controller: REST endpoint mapping & HTTP status codes.
  • service: Domain business rules & gamification logic.
  • strategy: Swappable streak evaluation engines.
  • repository: Data access abstraction layer.
Frontend React Modules:
  • components/QuestBoard.jsx: Main habit listing view.
  • components/HeroStats.jsx: HP/XP progression bars.
  • components/HabitCard.jsx: Individual quest item card.
  • services/habitService.js: Isolated REST client.
// frontend/src/services/habitService.js - Modular REST API Client
const API_BASE = '/api';
export const habitService = {
  async getHabits(userId = 'user-default') {
    const res = await fetch(`${API_BASE}/habits?userId=${userId}`);
    if (!res.ok) throw new Error('Failed to fetch quests');
    return res.json();
  },
  async completeHabit(habitId, userId = 'user-default') {
    const res = await fetch(`${API_BASE}/habits/${habitId}/complete?userId=${userId}`, { method: 'POST' });
    return res.json();
  }
};

Software Design Document • DA-2 1. Design Principles: High Cohesion & Low Coupling

C. High Cohesion (Single Responsibility Principle)

Cohesion measures how tightly bound the internal tasks of a module are. High cohesion guarantees that each class has only one reason to change:

  • StreakCalculationService: Dedicated solely to tracking consecutive completion dates, streak increments, and midnight streak breaks. It never processes HTTP requests or user passwords.
  • GamificationService: Dedicated solely to RPG health calculations, gold rewards, and leveling algorithms.
  • HabitController: Dedicated solely to HTTP transport concerns: JSON validation, status codes, and routing.
// StreakCalculationService.java - Highly Cohesive Domain Service
@Service
public class StreakCalculationService {
    private final StreakStrategy streakStrategy;

    @Autowired
    public StreakCalculationService(StreakStrategy streakStrategy) {
        this.streakStrategy = streakStrategy;
    }

    public void processHabitCompletion(Habit habit, LocalDate date) {
        int updatedStreak = streakStrategy.calculateNewStreak(habit, date);
        habit.setCurrentStreak(updatedStreak);
        if (updatedStreak > habit.getLongestStreak()) {
            habit.setLongestStreak(updatedStreak);
        }
        habit.setCompletedToday(true);
        habit.setLastCompletedDate(date);
    }
}

D. Low Coupling (Inversion of Control & Loose Service Dependencies)

Coupling measures interdependencies between modules. Tight coupling produces fragile code where changes cascade uncontrollably. HabitForge guarantees Low Coupling through:

  • Constructor Dependency Injection: Services never instantiate concrete dependencies with new. The Spring IoC container injects abstractions dynamically at runtime.
  • Stateless REST Communication: The frontend and backend communicate exclusively over standard JSON HTTP contracts, eliminating binary dependencies between Java and JavaScript.
// HabitServiceImpl.java - Loosely Coupled via Constructor Dependency Injection
@Service
public class HabitServiceImpl implements HabitService {
    private final HabitRepository habitRepository;
    private final StreakCalculationService streakCalculationService;
    private final GamificationService gamificationService;

    @Autowired
    public HabitServiceImpl(HabitRepository habitRepository,
                            StreakCalculationService streakCalculationService,
                            GamificationService gamificationService) {
        this.habitRepository = habitRepository;
        this.streakCalculationService = streakCalculationService;
        this.gamificationService = gamificationService;
    }

    @Override
    public HabitResponseDto completeHabit(String habitId, String userId) {
        Habit habit = habitRepository.findById(habitId).orElseThrow();
        if (!habit.isCompletedToday()) {
            streakCalculationService.processHabitCompletion(habit, LocalDate.now());
            habitRepository.save(habit);
            gamificationService.awardHabitRewards(userId, habit.getXpReward());
        }
        return mapToDto(habit);
    }
}

2. High-Level Architecture

HabitForge implements a 3-Tier Layered Client-Server Architecture orchestrated via Docker Compose. The system is segregated into three distinct tiers:

Figure 2.1: Updated HabitForge High-Level Layered System Architecture Diagram (Draw.io source)

Architectural Style Selected & Engineering Rationale

We selected the 3-Tier Layered Client-Server Architectural Style over monolithic server-rendered MVC or event-driven microservices for several strategic reasons:

  1. Strict Separation of Concerns: Visual presentation (React), gamification business rules (Spring Boot), and persistence (MongoDB) run in isolated containers. Changes to UI themes never risk corrupting streak algorithms.
  2. Independent Scalability: The static React Vite application can be deployed to global edge CDNs (Cloudflare/Vercel) while backend computing clusters scale independently to handle peak midnight cron loads.
  3. Multi-Client Support: The Spring Boot API exposes pure stateless JSON endpoints. Developing native mobile apps (iOS/Android in Flutter or React Native) requires zero backend changes.
  4. Infrastructure Parity (Docker Compose): Multi-container orchestration standardizes ports, volumes, and networks (seproject_default) across developer workstations and production servers.

Software Design Document • DA-2 4. Design Decisions & Technical Trade-offs

4. Key Design Decisions & Why

High-reliability engineering requires balancing trade-offs between speed, maintainability, and scalability. Below is an analysis of the 5 key architectural decisions made in HabitForge:

Decision Choice Selected & Rationale Alternative Rejected & Why
1. Client Rendering Architecture React 18 + Vite (SPA): Sub-100ms client route transitions and instantaneous optimistic UI checkoffs. Vital for gamified tactile feedback. Multi-Page MVC (Thymeleaf/JSP): Full-page browser refreshes break player immersion and make animated progress gauges feel sluggish.
2. Backend Layering & Separation Controller-Service-Repository with DTOs: Strict boundaries prevent database leakage and allow isolated unit testing. Flat Controller-Entity Architecture: Direct binding of database models to HTTP endpoints creates critical security vulnerabilities.
3. Database Paradigm Document NoSQL (MongoDB): Habit objects have variable metadata (schedules, check-in history, badges) that map naturally to JSON documents. Strict Relational SQL (PostgreSQL): Requires complex multi-table joins for simple daily check-in evaluations and schema migrations.
4. Health Penalty Synchronization Server-Authoritative Midnight Cron: Backend @Scheduled task deducts HP and resets streaks at 23:59:59 server time. Client-Triggered Local Evaluation: Relying on client clocks allows users to manipulate device time to bypass health penalties and fake streaks.
5. Session & Auth Architecture Stateless JWT (JSON Web Tokens): Self-contained signed tokens allow the Spring Boot API to scale horizontally without session clustering. Server-Side Stateful Sessions: Storing session states in server RAM creates single points of failure and complicates cloud redeployments.

Maintainability & Technical Debt Mitigation

By implementing the Strategy Pattern for streak evaluation (StreakStrategy), we satisfy the Open/Closed Principle: new streak rules (such as weekend exemptions or illness freezes) can be introduced as new strategy classes without modifying core habit services.

Persistence Decoupling: The repository layer is encapsulated behind the HabitRepository interface. If storage demands exceed single-instance MongoDB capacity, the persistence engine can be swapped for a distributed cluster without modifying controller or service logic.
